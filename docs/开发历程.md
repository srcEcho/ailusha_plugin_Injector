### Bug #3 修复确认

| 版本 | Hook 方式 | 成功率 |
|------|----------|:--:|
| v46 (P5/U5, 动态payload) | 每次 unhook/rehook | ~20% |
| v46 (P5/U5, 硬编码payload) | 每次 unhook/rehook | ~37% |
| **v50 (MinHook)** | **永久 trampoline，永不 unhook** | **~100%** |

### MinHook vs P5/U5 对比

| | P5/U5 (v46) | MinHook (v50) |
|---|------|------|
| Hook 安装 | 手写 5 字节 JMP rel32 | hde32 反汇编计算完整指令边界 |
| 运行时行为 | 每次 ReadFile 都 U5→P5 | 永不 unhook |
| 竞态窗口 | 每次调用 ~1μs | 零 |
| 代码量 | ~20 行 | ~300 行（静态编译进 DLL） |
| 可靠性 | ~20% | ~100% |

### Bug #3 竞态机制

```
H_RF 每次调用：
  U5(gA_RF, gO_RF);     // 暂时恢复 gO_RF（DllMain 时保存的字节）
  r = g_RealRF(...);      // 调用真正的 ReadFile
  P5(gA_RF, H_RF);       // 重新安装我们的 JMP
  //      ↑ 这个几微秒窗口里，如果另一个线程也调 ReadFile：
  //        → 看到 gO_RF 状态（可能是原始字节，也可能是 Enigma 的 JMP）
  //        → 绕过了 Enigma VFS hook → 读到未解密数据 → 0xC0000005
```

**关键：v46 的 BuildPayload 在 hook 内调 ReadFile → 嵌套 U5→P5 → 竞态窗口翻倍 → 成功率更低（20% vs 37%）**

### 修复方向：MinHook

MinHook 库提供以下 API（v50 使用）：
- `MH_Initialize` / `MH_CreateHookApi` / `MH_EnableHook` / `MH_Uninitialize`
- `hde32_disasm`（长度反汇编器，配合 MinHook 计算指令边界）
- 不 unhook/rehook，Hook 永远稳定

## 核心发现: 残留进程根因

**version.dll 代理转发导致进程无法正常退出。** 只要导出函数(GetFileVersionInfo等)有实际的转发逻辑(LoadLibraryExA或GetModuleHandleA,无论ATTACH还是延迟加载),进程关闭后残留。导出返回0 → 无残留。

**根本原因**: 系统version.dll已被Enigma加载(0x727C0000)。我们的version.dll再次引用它(同名模块),Windows loader在卸载时产生模块依赖冲突,进程无法退出。

**最终方案**: version.dll导出全返回0,不做代理转发。NW.js 0.93不需要版本信息。

1. **V8重入墙**：V8执行栈内任何分配型API（NFU/Compile/Integer::New）必定崩溃

## 最终工作架构

```
Game.exe (浏览器进程)
  ├── version.dll (我们的 DLL)
  │     ├── 导出函数 return 0 (不做version代理,避免残留进程)
  │     └── Hook ReadFile → 检测main.js → 注入$plugins.push(QuestLog)
  │
  ├── Enigma VFS fallback: www/js/plugins/QuestLog.js (不存在于VFS)
  │     → 自动fallback到磁盘 www/js/plugins/QuestLog.js
  │
  └── 磁盘文件 (放在 www/js/plugins/ 下,Enigma自动找到):
        QuestLog.js, quests.json, routes.json
```

**关键机制**: 
1. main.js注入让PluginManager去找QuestLog插件
2. Enigma VFS找不到QuestLog.js → 自动fallback到磁盘 www/ 路径
3. 不需要CreateFileW重定向,不需要CreateProcessW Hook
4. version.dll不做代理转发 → 无残留进程
