## 一、总体架构

```
Game.exe (EnigmaVB打包, 1.4GB, 32-bit)
  │
  ├── .enigma1 节 → VFS文件表 + 4176个明文文件
  ├── .enigma2 节 → aplib压缩的Enigma Loader DLL
  │
  ├── 浏览器进程 (NW.js 主进程, 70+ DLL)
  │     ├── nw.dll @ 0x10000000 (84.8MB, 10,480 exports)
  │     ├── nw_elf.dll @ 0x08280000 (472KB loader)
  │     ├── version.dll ← 我们的DLL (版本代理 + CreateFileW/ReadFile双Hook)
  │     │     ├── Hook CreateFileW → 检测QuestLog文件 → 磁盘重定向
  │     │     ├── Hook ReadFile → 检测main.js → 注入$plugins.push()
  │     │     └── Hook CreateProcessW → 注入renderer_hook.dll到渲染进程
  │     └── 磁盘文件: QuestLog.js (55KB), quests.json (23KB), routes.json (3.9MB)
  │
  └── 渲染进程 (NW.js renderer, 27 DLL, 零窗口)
        ├── nw_elf.dll @ 0x10000000 (84.8MB, 与浏览器nw.dll同一二进制)
        └── renderer_hook.dll (备用, 当前方案不需要)
```

## 二、核心突破

### 突破1：JS文件在浏览器进程加载（不是渲染进程！）

之前所有24条路线都假设 JS 在渲染进程中执行和加载。**NtReadFile/ReadFile hook 在渲染进程只能看到 PE/DLL 加载流量**。

v32 在浏览器进程 Hook ReadFile → 第734次调用截获 `plugins.js` MID 签名 → **证明 JS 明文流经浏览器进程 kernel32 ReadFile**。

### 突破2：main.js 是理想注入点

v33 文本扫描器捕获了完整文件加载顺序：
```
index.html → game.css → pixi.js → pixi-tilemap.js → pixi-picture.js →
fpsmeter.js → lz-string.js → iphone-inline-video.js → rpg_core.js →
rpg_managers.js → rpg_objects.js → rpg_sprites.js → rpg_scenes.js →
rpg_windows.js → plugins.js → main.js
```

- **main.js** 只有 270 字节，32KB buffer 有大量空间
- 在 `PluginManager.setup($plugins)` 之前插入 QuestLog 注册
- 在所有插件加载之后才执行 — 时机完美

### 突破3：CreateFileW 磁盘重定向绕过 Enigma VFS 限制

Enigma VFS 管理 `www/` 目录，返回无效句柄给不存在的文件。
将 QuestLog 文件放在游戏根目录（Enigma 不管理），CreateFileW hook 重定向请求。

## 三、最终方案（v36）

### version.dll 的工作

```
DllMain (PROCESS_ATTACH):
  1. Hook CreateFileW → H_CreateFileW
  2. Hook ReadFile → H_ReadFile
  
H_ReadFile 每次调用:
  - 检查buffer内容是否含 "// main.js"
  - 如果是 → 在 "PluginManager.setup($plugins)" 前插入 $plugins.push(...)
  - 调整 *lpBytesRead 反映新大小
  
H_CreateFileW 每次调用:
  - 检查文件名是否为 QuestLog.js / quests.json / routes.json
  - 如果是 → 重定向到游戏根目录的磁盘文件（绕过Enigma VFS）
  - 返回磁盘文件句柄
```

### 磁盘文件部署

```
游戏根目录/
├── Game.exe
├── version.dll          ← 浏览器进程 DLL
├── renderer_hook.dll    ← 渲染进程 DLL（备用）
├── QuestLog.js          ← 任务引导引擎 (55KB, 993行)
├── quests.json          ← 29个任务数据 (23KB)
└── routes.json          ← BFS地图路由 (3.9MB)
```

### 编译方法

```bash
# 必须通过 MSYS2 shell（Git Bash 中 gcc 路径映射有问题）
cp dev/version_proxy_v36.c /c/tmp/v36.c
/c/Programs/msys64/msys2_shell.cmd -mingw32 -defterm -no-start -c \
  'gcc -shared -s -Os -static -Wl,--kill-at -o /c/tmp/v36.dll /c/tmp/v36.c -lkernel32 && echo SUCCESS'
cp /c/tmp/v36.dll 游戏目录/version.dll
```

## 四、路线演进全记录

### Phase 1-2: 文件系统 + CDP（全失败）
Chromium 不走 kernel32/ntdll 读 JS（在渲染进程）。NW.js 0.93 不支持远程调试。

### Phase 3: QPC + V8 内部（全失败）
V8 重入墙：执行栈内任何分配型 API 必定崩溃。NW.js 不使用公开 V8 API。

### Phase 4: 延迟执行 + Inspector（全失败）
零窗口、无消息泵、connect()重入。

### Phase 5: 边界回调 + 其他AI方案（全失败）
BeforeCallEntered触发但NFU崩溃。--load-extension不支持。NtReadFile拦截到容器数据。

### Phase 6: GLM 深入分析（2026-08-05）
evbunpack: 4176文件全明文。内存扫描: JS正文非常驻(found=0)。probe_ntread v2: DllMain死锁。

### Phase 7: 浏览器进程 ReadFile Hook（2026-08-05 — **突破**）
v32: 浏览器进程 MID HIT！v33: 文件加载顺序确认。v34: main.js注入成功！
v35: CreateFileW+ReadFile双重服务。v36: **磁盘重定向 — 方案可行！**

## 六、关键教训

1. **进程边界至关重要**：JS 文件在浏览器进程加载，不在渲染进程。所有针对渲染进程的文件系统 hook 都是徒劳的。
2. **从下层往上层突破**：V8 层（最底层）→ 文件系统层（中间层）→ 成功的突破在文件系统层。
3. **Enigma VFS 的盲区**：不管理 `www/` 之外的路径，这成为磁盘重定向的基础。
4. **main.js 是完美目标**：体积小（270B）、位置关键（PluginManager.setup调用点）、时机完美（所有插件加载后）。
5. **编译环境陷阱**：MSYS2 gcc 的 `--prefix` 导致 Git Bash 中编译失败，必须通过 MSYS2 shell 编译。
6. **Hook 库选型至关重要**：手写 P5/U5 与 Enigma Hook 竞态导致 ~20% 成功率。MinHook 库的永久 trampoline 可消除竞态。详见 Bug #3 分析。

## 七、Hook 竞态分析（2026-08-07 实证）

### 问题
v46 DLL 间歇性导致 Game.exe 0xC0000005 崩溃（~20% 成功率）。

### 根因
ReadFile Hook 中 `U5→真ReadFile→P5` 的 unhook/rehook 窗口：
```
H_RF:  U5(恢复gO_RF) → g_RealRF(...) → P5(重新写JMP)
              ↑ 窗口期另一个线程 ReadFile → 中间状态的hook → 0xC0000005
```

### 实证（Test A/B/C 三对照）
| 测试 | 条件 | 成功率 |
|------|------|:--:|
| Test A | 版本桩 only | 100% |
| Test B | Hook only（无版本桩） | DLL 加载失败 |
| Test C | 版本桩 + Hook(硬编码) | ~37% |
| v46 | 版本桩 + Hook(动态payload) | ~20% |

### 修复方向 → 已实现 (v50)
v50 版本使用 **MinHook** 库替代 P5/U5，100% 成功率验证通过：
- `MH_CreateHookApi(L"kernel32.dll", "ReadFile", H_RF, &g_RealRF)` 一次性安装 trampoline
- `hde32_disasm` 长度反汇编器保证完整指令边界
- 永不 unhook → 零竞态
- 源码: `src/mainline/version_proxy_v50_minhook.c`
