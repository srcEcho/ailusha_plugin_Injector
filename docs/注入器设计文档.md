# 艾露莎注入器 v1.0 — 设计文档

> 状态：设计定稿 | 2026-08-05

## 一、产品定位

- **名称**：艾露莎注入器 (Elusha Injector)
- **版本**：1.0
- **支持游戏版本**：1.051（主页面标题栏展示，不做校验）
- **对标游戏**：世間知らずの猫エルーシャ (EnigmaVB + NW.js 0.93 + RPG Maker MV)
- **普通用户**：双击打开，开关插件，启动游戏。不需要说明书。
- **插件开发者**：CLI 驱动，所有功能可通过命令行调用。AI 友好。

## 二、插件格式 `.elsmod`

- **本质**：zip 压缩包
- **内部结构**：
  ```
  PluginName.elsmod
  ├── www/
  │   └── js/
  │       └── plugins/
  │           ├── <PluginName>.js        ← 插件本体
  │           └── data/
  │               └── <PluginName>_<Author>/   ← 插件数据（必须以此格式命名）
  │                   └── plugin.json    ← 元数据（必须）
  ```

### 2.1 plugin.json 规范

```json
{
  "name": "QuestLog",
  "version": "2.0.0",
  "author": "QuestMod",
  "description": "任务引导系统。按 Q 打开任务日志。",
  "gameVersion": "1.051",
  "dependencies": [],
  "conflicts": []
}
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | ✅ | 插件唯一标识 |
| `version` | ✅ | 语义化版本 |
| `author` | ✅ | 插件作者 |
| `description` | ✅ | 简介 |
| `gameVersion` | ✅ | 支持的猫游戏版本 |
| `dependencies` | 否 | 依赖列表 |
| `conflicts` | 否 | 冲突列表 |

### 2.2 依赖/冲突格式

```json
{
  "dependencies": [
    { "name": "MiniMap", "author": "elusha_mod", "version": ">=0.6.0" }
  ],
  "conflicts": [
    { "name": "OldMapMod" }
  ]
}
```

- `name`：必须
- `author`：可选（不填 = 匹配任何作者）
- `version`：可选（`>=` / `=` / `<=`）

### 2.3 为什么 plugin.json 放在 data/名称_作者/ 下

不同作者可能制作同名插件。`plugin.json` 放在 `data/<PluginName>_<Author>/` 下实现作者级隔离，避免互相覆盖。

### 2.4 插件命名冲突

- **同一作者、同名插件 → 版本共存**。UI 下拉选择激活版本。老版本 elsmod 保留在 `elsmod_data/`。
- **不同作者、同名插件 → 拒绝并提示**"名称冲突。建议联系作者在名称中标注作者后缀"。

### 2.5 标准项目模板

`--cli template --name <n> --author <a> --dir <d>` 生成：

```
<指定目录>/
└── www/
    └── js/
        └── plugins/
            ├── <插件名称>.js
            └── data/
                └── <插件名称>_<作者>/
                    └── plugin.json
```

打包时严格按此结构检测。格式不符 → 拒绝打包并提示具体问题。

## 三、目录结构

```
游戏目录/
├── Game.exe
├── version.dll                   ← 注入器核心 DLL（exe 内嵌，启动时解出）
├── ElushaInjector.exe            ← 注入器 GUI（本程序）
├── UninstallElusha.exe           ← 卸载器（自动生成）
├── elsmod_data/                  ← 全部状态集中于此
│   ├── registry.json             ← 注册表（导入记录 + 启用状态 + loadOrder）
│   ├── tmp/                      ← 导入临时目录（事务性解压）
│   ├── QuestLog-v2.0.0.elsmod    ← 源文件（命名规则：{name}-{version}.elsmod）
│   ├── MiniMap-v0.6.2.elsmod
│   └── ...
├── www/js/plugins/               ← 已安装插件（活动副本，从 elsmod 解压）
│   ├── QuestLog.js
│   └── data/
│       └── QuestLog_QuestMod/
│           └── plugin.json
└── ...
```

砍掉了 `.mod-manager/` 目录。`elsmod_data/` 是唯一的状态目录——保留它就是保留全部。

## 四、环境检测（启动时自动执行，无需用户确认）

```
ElushaInjector.exe 启动
  → 检测当前目录是否包含 Game.exe
  → 是游戏目录：
      → 创建 www/js/plugins/（如不存在）
      → 创建 www/js/plugins/data/（如不存在）
      → 创建 elsmod_data/（如不存在）
      → 创建 elsmod_data/tmp/（如不存在）
      → 解出 UninstallElusha.exe（如不存在）
      → 解出 version.dll（如不存在）
      → 扫描 elsmod_data/*.elsmod → 与 registry.json 比对
        → 有 elsmod 但 registry 无记录 → 自动恢复
        → 有记录但文件缺失 → 标记为"破损"
  → 不是游戏目录：
      → 弹窗 "请将本程序放到游戏目录下运行"
      → 退出
```

### 4.1 不一致检测与修复

- 启动时检测 `registry.json` 记录的 `files` 是否真实存在于 `www/js/plugins/`
- 存在记录但文件缺失 → UI 标记为"破损"（红色），开关禁用
- 提供"修复"按钮 → 从 `elsmod_data/` 中的源文件重新解压

### 4.2 卸载后重装恢复

如果用户卸载时保留了 `elsmod_data/`，重装注入器后：
- 启动时扫描 `elsmod_data/*.elsmod`
- 与 registry.json 比对 → 有 elsmod 但 registry 无记录 → 自动恢复注册表条目

## 五、游戏运行时的操作限制

Game.exe 在运行中时：
- **禁止**：导入、卸载、开关切换、排序调整、修复
- 任何修改操作均弹窗"请先关闭游戏"
- "关闭"按钮仍然可用（只退出注入器）

### 6.3 导入流程

```
用户触发导入
  → 解析 .elsmod → 读取 plugin.json
  → 检查必填字段 → 缺失则拒绝并提示
  → 检查目录格式 → 不符则拒绝并提示
  → 检查重复 → elsmod_data/ 已有同名+同版本 elsmod → 弹窗"已存在"
  → 检查冲突（同名+同作者 → 版本共存 / 同名+不同作者 → 拒绝）
  → 检查依赖 → 缺失则警告但仍允许导入（只是不能启用）
  → 解压到 elsmod_data/tmp/（临时）
  → 验证 tmp/ 内文件完整性
  → 移动到 www/js/plugins/（正式位置）
  → 复制 .elsmod 到 elsmod_data/（文件名为 {name}-{version}.elsmod）
  → 清理 tmp/
  → 更新 registry.json
  → 触发拓扑排序 → 更新 loadOrder
  → 刷新 UI
```

**事务性保障**：先解压到临时目录 → 验证通过 → 一次性移到最终位置。如果中间失败，删除 tmp 目录，不影响现有插件。

### 6.4 文件生命周期（卸载 → 重装 → 升级）

核心原则：`registry.json` 的 `files` 列表精确记录了"插件的哪些文件来自 elsmod"。不在列表中的都是用户数据。

**卸载时**：
```
遍历 record.files → 逐一删除 → 保留不在 files 列表中的任何文件
```
→ `data/名称_作者/` 下插件运行时产生的用户数据（存档、配置缓存）不丢失。

**重装/升级时**：
```
1. 遍历旧 record.files → 逐一删除
2. 解压新版本到 tmp/
3. 遍历新版本所有文件 → 逐一检查：
   → 如果目标路径已存在文件，且该文件不在旧 record.files 列表中
   → 这意味着新版本的文件踩到了用户数据
   → 报错，列出冲突文件名，拒绝操作
   → 提示"请联系插件作者"
4. 全部检查通过 → 移动到正式位置
5. 更新 record.files 为新列表
```
→ 用户在旧版本间积累的数据夹在 `files` 列表差集中，不受任何影响。
→ 文件冲突是插件作者的职责，注入器只负责检测和报错。

## 七、插件加载顺序

### 7.1 拓扑排序算法

```
导入/启用/禁用任意插件 → 触发 reorder：
  1. 读取所有 enabled 插件的依赖关系
  2. 建图 → Kahn 拓扑排序
  3. 检测循环依赖 → 有则列出循环路径，标记相关插件为"冲突"，禁止启用
  4. 将排序结果写入 registry.json 的 loadOrder 字段
  5. DLL 注入时严格按 loadOrder 生成 $plugins.push() 序列
```

### 7.2 手动微调

每个条目旁有 ↑↓ 按钮。用户可在拓扑排序基础上微调相邻顺序。**立即写入 registry.json**。下次触发 reorder 时拓扑排序结果覆盖手动调整。

### 7.3 依赖连锁

- **启用 A（A 依赖 B，B 未安装）**：拒绝启用，提示"缺少依赖：B"
- **启用 A（A 依赖 B，B 已安装但禁用）**：弹窗"B 将被一起启用。确认？"
- **禁用 B（A 依赖 B）**：弹窗"A 依赖 B，将一起禁用 A。确认？"
- **卸载 B（A 依赖 B）**：弹窗"A 依赖 B，将一起卸载 A。确认？"

## 九、DLL 运行时行为

### 9.1 version.dll（exe 内嵌，启动时解出）

- 导出函数全部 `return 0`（不做 version 代理 → 无残留进程）
- Hook kernel32!ReadFile
- 检测 main.js → 读取 `elsmod_data/registry.json`
- 按 `loadOrder` 顺序，对每个 `enabled: true` 的插件生成 `$plugins.push()`
- 注入到 `PluginManager.setup($plugins)` 之前

### 9.2 编译

```bash
cp version_proxy_v36_final.c /c/tmp/v36.c
/c/Programs/msys64/msys2_shell.cmd -mingw32 -defterm -no-start -c \
  'gcc -shared -s -Os -static -Wl,--kill-at -o /c/tmp/v36.dll /c/tmp/v36.c -lkernel32'
```

## 十、注册表

`elsmod_data/registry.json`——注入器唯一状态文件：

```json
{
  "version": 1,
  "loadOrder": ["MiniMap", "QuestLog"],
  "records": [
    {
      "name": "QuestLog",
      "author": "QuestMod",
      "version": "2.0.0",
      "enabled": true,
      "source": "elsmod_data/QuestLog-v2.0.0.elsmod",
      "installedAt": "2026-08-05T14:30:00",
      "files": [
        "QuestLog.js",
        "data/QuestLog_QuestMod/plugin.json",
        "data/QuestLog_QuestMod/quests.json",
        "data/QuestLog_QuestMod/routes.json"
      ]
    }
  ]
}
```

- `loadOrder`：DLL 严格按此数组顺序注入
- `source`：elsmod 文件名（`{name}-{version}.elsmod`）
- `enabled`：DLL 只注入此字段为 true 的插件
- `files`：相对于 `www/js/plugins/` 的文件列表，用于卸载和不一致检测

- 拖放 `.elsmod` → 触发导入

## 十二、开发者模式

### 12.1 三种启动模式

| 启动方式 | 模式 | 界面 |
|---------|------|------|
| `ElushaInjector.exe` | 普通用户 | GUI 主页面 |
| `ElushaInjector.exe --dev` | 插件开发者 | GUI 开发者面板（独立窗口，包含普通用户所有功能） |

### 12.2 CLI 命令

```bash
# 插件管理
ElushaInjector.exe --cli list [--enabled|--disabled] [--output json]
ElushaInjector.exe --cli info <name> [--output json]
ElushaInjector.exe --cli enable <name>
ElushaInjector.exe --cli disable <name>

# 安装/卸载
ElushaInjector.exe --cli install <file.elsmod> [--force]
ElushaInjector.exe --cli uninstall <name>

# 导入记录
ElushaInjector.exe --cli imported [--output json]

# 打包/解包（开发者）
ElushaInjector.exe --cli pack <dir> -o <out.elsmod>
ElushaInjector.exe --cli unpack <file.elsmod> -o <dir>

# 模板生成（开发者）
ElushaInjector.exe --cli template --name <n> --author <a> --dir <d>

# 部署
ElushaInjector.exe --cli deploy [--force]

# 启动
ElushaInjector.exe --cli launch [--skip-plugins]

# 配置
ElushaInjector.exe --cli config --show [--output json]

# 工具
ElushaInjector.exe --cli tools list
ElushaInjector.exe --cli tools open <name>

# 系统
ElushaInjector.exe --cli register
ElushaInjector.exe --cli unregister
ElushaInjector.exe --cli version
```
