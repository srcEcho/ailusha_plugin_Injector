# QuestLog 插件注入 — 最终解决方案

> 2026-08-05 | 状态：**✅ 方案可行**
> 经过 36+ 版本的 DLL 迭代、24+ 条路线的穷举测试，终于找到可行的注入方案。

---

## 一、最终方案概览

### 核心思路：**浏览器进程 ReadFile + CreateFileW 双重 Hook + 磁盘文件重定向**

```
version.dll (浏览器进程)
  ├── Hook kernel32!CreateFileW → 检测QuestLog文件请求 → 重定向到磁盘
  ├── Hook kernel32!ReadFile → 拦截main.js读取 → 注入QuestLog注册
  └── Hook kernel32!CreateProcessW → 注入renderer_hook.dll到渲染进程
```

### 工作流程

1. Game.exe 启动 → 加载 version.dll (Enigma 导入 DLL)
2. version.dll DllMain:
   - Hook `kernel32!CreateFileW` (检测 QuestLog 文件名)
   - Hook `kernel32!ReadFile` (拦截 JS 文件读取)
3. 浏览器进程加载 `main.js` → ReadFile hook 检测到 `// main.js` 头部
4. 注入代码：`$plugins.push({"name":"QuestLog","status":true,...});` 到 `PluginManager.setup($plugins)` 之前
5. PluginManager 尝试加载 `js/plugins/QuestLog.js` → CreateFileW hook 检测到文件名
6. CreateFileW hook 重定向到磁盘文件 `QuestLog.js`（游戏根目录，Enigma VFS 不管理此路径）
7. 同理重定向 `quests.json`、`routes.json` 数据文件
8. QuestLog 插件成功加载

## 二、关键发现时间线

### Phase 1: 渲染进程路线 (全部失败)
- V8 重入墙 → 否決
- Inspector CDP → 否決
- NtReadFile hook → 否決（只看到容器数据）
- 零窗口 → 否決 Windows 消息路线

### Phase 2: 浏览器进程路线 (突破)
- **v32**: 在浏览器进程 Hook ReadFile → **发现 MID HIT！** plugins.js 明文流经 kernel32 ReadFile
- **v33**: 文本扫描器确认文件加载顺序：index.html → pixi.js → rpg_core.js → ... → **main.js**
- **v34**: 首次主动注入 → main.js 被成功修改，$plugins 数组被注入 QuestLog 条目

### Phase 3: 文件服务 (突破)
- **v34 报错**: `Failed to load: js/plugins/QuestLog.js` — QuestLog.js 不在 Enigma VFS 中
- **v35**: 尝试通过 ReadFile 服务 QuestLog.js 内容（CreateFileW 返回无效句柄，ReadFile 未被调用）
- **v36**: **CreateFileW 磁盘重定向** — 检测 QuestLog 文件请求，重定向到游戏根目录磁盘文件

## 三、技术细节

### 3.1 main.js 注入

目标文件：`www/js/main.js`（270 字节）

```javascript
// 原始内容：
PluginManager.setup($plugins);
window.onload = function() {
    SceneManager.run(Scene_Boot);
};

// 注入后：
$plugins.push({"name":"QuestLog","status":true,"description":"","parameters":{}});
PluginManager.setup($plugins);
window.onload = function() {
    SceneManager.run(Scene_Boot);
};
```

- 注入点：`PluginManager.setup($plugins)` 之前（偏移 172）
- Payload：84 字节
- Buffer：32KB（270 字节使用中，有充足空间）

### 3.2 CreateFileW 磁盘重定向

检测到以下文件名时重定向：
- `QuestLog.js` → 游戏根目录 `QuestLog.js`
- `quests.json` → 游戏根目录 `quests.json`  
- `routes.json` → 游戏根目录 `routes.json`

关键：这些文件在游戏根目录（非 `www/` 下），Enigma VFS 不管理此路径，透传到真实文件系统。

### 3.3 磁盘文件清单

```
游戏根目录/
├── Game.exe
├── version.dll          ← 浏览器进程注入 DLL
├── renderer_hook.dll    ← 渲染进程注入 DLL（备用）
├── QuestLog.js          ← 任务引导插件 (55KB)
├── quests.json          ← 任务数据 (23KB)
└── routes.json          ← 地图路由数据 (3.9MB)
```

### 3.4 DLL 编译约束

- **编译器**：MSYS2 MinGW 32-bit (`i686-w64-mingw32-gcc`)
- **必须通过 MSYS2 shell 编译**：`msys2_shell.cmd -mingw32 -defterm -no-start -c 'gcc ...'`
- **编译参数**：`-shared -s -Os -static -Wl,--kill-at`
- **注意**：Git Bash 中直接运行 gcc 会失败（`--prefix=/mingw32` 路径映射问题）

## 四、已验证的架构发现

### 4.1 NW.js 0.93 进程模型

```
浏览器进程 (Game.exe 主进程)
  ├── nw.dll @ 0x10000000 (84.8MB, 10,480 exports) ← V8 + Chromium + Node.js
  ├── nw_elf.dll @ 0x08280000 (472KB) ← 小型 loader
  ├── ffmpeg.dll (3.1MB)
  └── 70+ 系统 DLL

渲染进程 (--type=renderer)
  ├── nw_elf.dll @ 0x10000000 (84.8MB, 10,480 exports) ← 与浏览器 nw.dll 同一二进制
  ├── ffmpeg.dll (3.1MB)
  └── 27 个 DLL 总计（无窗口、无消息泵）
```

### 4.2 JS 文件加载机制

- JS 文件通过 kernel32 `ReadFile` 加载（在**浏览器进程**中）
- 文件被 EnigmaVB 的 CreateFileW hook 拦截，从 overlay 返回明文
- 文件加载顺序：index.html → CSS → libs → rpg_core → rpg_managers → ... → plugins.js → main.js
- 大文件（如 rpg_core.js）以 32KB 块读取
- 小文件（如 main.js, 270B）单次读取

### 4.3 EnigmaVB VFS 行为

- 管理 `www/` 目录下的所有虚拟文件
- 对不存在的虚拟文件返回 `INVALID_HANDLE_VALUE`
- **不管理 `www/` 之外的路径** → 可透传到磁盘
- 4176 个文件全部明文存储（零压缩）

| 路线类别 | 数量 | 代表方案 | 死因 |
|---------|------|---------|------|
| V8 API 直接调用 | 6 | Script::Compile, NFU | V8 重入墙 |

| 模块扫描 | 2 | libuv, node.dll | 静态链接无独立 DLL |

## 七、后续优化方向

1. **消除磁盘文件依赖**：将 QuestLog.js 内容嵌入 version.dll，在 ReadFile 中直接服务
2. **全内存方案**：无需磁盘文件，完全通过 DLL 内置数据服务
3. **通用插件加载器**：扩展为支持任意 RPG Maker MV 插件的注入框架
4. **CDP 端口开启**：如果 NW.js 版本支持，可直接使用 CDP 做热重载
