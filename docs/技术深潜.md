## 三、三个 Bug 完整故事

### Bug #1: nw_elf.dll 报错

**症状**: Game.exe 启动弹出 "cannot load library nw_elf.dll"

**诊断过程**:
1. 旧 VBS 启动器在 TEMP 跑 → Game.exe 继承 TEMP 为 CWD
2. Enigma 初始化时在 CWD 找加密 VFS → TEMP 没有 → nw_elf.dll 报错
3. 曾误以为是 PyInstaller 的问题（实际是同时改了启动代码）

**根因**: Enigma 在当前工作目录找加密 VFS。错误 CWD → 找不到 nw_elf.dll。

**测试实证**: `Start-Process -WorkingDirectory 游戏目录` 立即修复。

**解决**: `subprocess.Popen([exe], cwd=gd)` 强制设工作目录。

---

### Bug #2: 版本 API 桩嫌疑（已排除）

**怀疑**: `GetFileVersionInfoSizeW` 等 6 个导出返回裸 0，调用方拿 0 当指针用 → 0xC0000005。

**测试**:
- Test A (纯版本桩, 无 Hook): 100% 成功 → **版本桩无辜**
- Test B (纯 Hook, 无版本桩): DLL 加载失败 → 版本桩必须存在

**结论**: 不是 Bug。版本桩安全。

---

### Bug #3: P5/U5 竞态（真正的元凶）

**症状**: ~20% 成功率，0xC0000005 崩溃，间歇性。跟启动方式无关（os.startfile/ShellExecuteEx/CreateProcess 都一样）。

**诊断过程**:
1. Test A (版本桩): 100% → 排除 Bug #2
2. Test C (Hook + 硬编码 payload, 无文件 I/O): ~37% → Hook 是根因
3. v46 原版 (Hook + 动态 payload): ~20% → BuildPayload 中的嵌套 ReadFile 加剧竞态

**根因机制**:
```
H_RF 每次调用:
  U5(gA_RF, gO_RF);     // 暂时恢复 DllMain 时保存的字节
  r = g_RealRF(...);      // 调用真正 ReadFile
  P5(gA_RF, H_RF);       // 重新安装 JMP
      ↑ 这个窗口里另一个线程的 ReadFile 看到中间状态
      → gO_RF 不一定包含 Enigma 的 hook
      → 绕过 Enigma VFS → 读到错误数据 → 0xC0000005
```

**v46 更差的原因**: BuildPayload 在 hook 内调 `ReadFile` → 嵌套 U5→P5 → 竞态窗口翻倍。

**MinHook 方案**: MinHook 用 `hde32_disasm` 计算完整指令边界，创建永久 trampoline，Hook 从不 unhook。v50 验证 100% 可靠。

**解决**: v50 用 MinHook 替换 P5/U5。Hook 永不 unhook。

## 四、P5/U5 vs MinHook 深度对比

### P5/U5 实现（v46）

```c
// 在 DllMain: 保存原始 5 字节，写 JMP H_RF
memcpy(gO_RF, gA_RF, 5);
g_RealRF = (RF_t)gA_RF;  // 指向 kernel32!ReadFile 的地址
P5(gA_RF, H_RF);          // 写 JMP rel32 → H_RF

// 在 H_RF 每次调用:
U5(gA_RF, gO_RF);         // 恢复原始 5 字节
r = g_RealRF(...);         // 调用 ReadFile（地址调用，不是 trampoline）
P5(gA_RF, H_RF);          // 重写 JMP
//   ↑ 问题: U5 恢复的是 DllMain 时的字节
//     如果 Enigma 在 DllMain 之后 hook，gO_RF 不含 Enigma
//     调用 g_RealRF 时 Enigma hook 被绕过
```

### MinHook 实现（v50）

```c
// 在 DllMain: 一次性安装
MH_Initialize();
MH_CreateHookApi(L"kernel32.dll", "ReadFile", H_RF, (LPVOID*)&g_RealRF);
MH_EnableHook(MH_ALL_HOOKS);
// g_RealRF 是 MinHook trampoline，不是 kernel32 地址

// 在 H_RF 每次调用:
r = g_RealRF(hf, buf, nb, lpb, lo);  // 纯调用，不 unhook
//   ↑ MinHook trampoline:
//     1. 执行被覆盖的完整指令（hde32 反汇编保证完整性）
//     2. JMP 回原始函数 + N 字节
//     3. 从不动 hook 的 JMP → 零竞态
```

### 为什么 P5/U5 5 字节不够

```
kernel32!ReadFile 原始代码:
  8B FF     mov edi, edi    ; hot-patch preamble (2 bytes)
  55        push ebp        ; 1 byte
  8B EC     mov ebp, esp    ; 2 bytes
  ...                        ; ← 我们的 JMP 跳到这里 (ReadFile+5)

就 5 字节恰好切断在 mov ebp, esp 后面 — 没有切碎指令。
```

但如果另一个 API 的开头不同：
```
  8B 4C 24 04  mov ecx, [esp+4]  ; 4 bytes
  85 C9        test ecx, ecx      ; 2 bytes
  ...
```
P5/U5 会在 `test ecx, ecx` 中间切断（只取 5 字节中的第 2 个字节），导致指令碎片。

MinHook 的 `hde32_disasm` 会分析每条指令长度，确保只切在完整指令边界。

## 五、MinHook 技术详解

### MinHook API

MinHook 1.3.3（BSD 协议）提供以下核心 API：

- `MH_Initialize()` — 初始化 hook 引擎
- `MH_CreateHook(pTarget, pDetour, &ppOriginal)` — 创建 hook，返回 trampoline
- `MH_CreateHookApi(L"dll", "func", pDetour, &ppOriginal)` — 按模块名+函数名创建 hook
- `MH_EnableHook(pTarget)` / `MH_DisableHook(pTarget)` — 启用/禁用单个 hook
- `MH_Uninitialize()` — 清理

### hde32 长度反汇编器

MinHook 内置 `hde32_disasm`，分析每条 x86 指令的长度。Hook 安装时，MinHook 反汇编目标函数开头，累计足够覆盖 5 字节 JMP 的完整指令，确保**从不在指令中间切断**。

```
例子： kernel32!ReadFile 开头
  8B FF     mov edi, edi     ; 2 bytes (hot-patch preamble)
  55        push ebp          ; 1 byte
  8B EC     mov ebp, esp      ; 2 bytes
  Total: 5 bytes ← 恰好对齐，直接 patch 5 字节

反例：如果另一个函数开头是
  8B 4C 24 04  mov ecx, [esp+4]  ; 4 bytes
  85 C9        test ecx, ecx       ; 2 bytes
  P5/U5 切 5 字节 → 把 test ecx, ecx 切成两半 → 指令碎片
  MinHook 反汇编后切 6 字节 → 两条指令都完整
```

### 永久 Trampoline 机制

```
安装时 (DllMain):
  kernel32!ReadFile: [原始 5 字节] → [JMP → H_RF]
  Trampoline:        [原始 5 字节] + [JMP → ReadFile+5]
  g_RealRF = Trampoline 地址

运行时 (H_RF 每次调用):
  r = g_RealRF(hf, buf, nb, lpb, lo)
    → Trampoline: 执行原始 5 字节 → JMP ReadFile+5 → 真实 ReadFile 执行
    → 返回到 H_RF
    → Hook 永远不动 → 零竞态
```

### v50 使用方式

```c
// DllMain: 一次性安装
MH_Initialize();
MH_CreateHookApi(L"kernel32.dll", "ReadFile", H_RF, (LPVOID*)&g_RealRF);
MH_EnableHook(MH_ALL_HOOKS);

// H_RF: 直接调用 trampoline，无 unhook
BOOL r = g_RealRF(hf, buf, nb, lpb, lo);

// DllMain DETACH: 清理
MH_DisableHook(MH_ALL_HOOKS);
MH_Uninitialize();
```

## 六、Bootstrap 注入机制

### 原理

Bootstrap 不修改 `$plugins` 数组，而是**替换游戏已加载文件的来源**。

```
正常流程:
  Game.exe → CreateFileW("EventInformation.js") → Enigma VFS → 原版文件

Bootstrap 流程:
  Game.exe → CreateFileW("EventInformation.js") → DLL 重定向 → Bootstrap.js (磁盘)
    → Bootstrap 内部:
      ① fs.readFileSync("originals/EventInformation.js") → eval (原版照跑)
      ② fs.readFileSync("www/js/plugins/ModPlugin.js") → eval (MOD 加载)
```

### 为什么 Bootstrap

| | main.js 注入 | Bootstrap |
|---|---|---|
| 加插件 | ✅ push | ✅ eval |
| 删插件 | ❌ | ✅ 重定向 plugins.js |
| 覆盖文件 | ❌ | ✅ CreateFileW |
| VFS fallback 依赖 | 是 | 否 (fs 直读) |
| 配置复杂度 | 低 | 中 (Python 自动生成) |

### 文件大小限制

Bootstrap 必须 ≤ 原版文件大小。Enigma VFS 记录原文件大小，游戏分配对应缓冲。超过原大小的 Bootstrap 尾部会被截断。

解决方案：Bootstrap 是压缩加载器（~250 字节），原版代码放 `originals/` 目录，用 `fs.readFileSync` 读取。这样 Bootstrap 体积远小于任何原版文件。

### 防死循环

Bootstrap 读取 `originals/` 目录下的原版文件时，DLL 检测路径中 `originals` 字样，跳过重定向。

### 配置

```json
{
  "injection_mode": "bootstrap",
  "redirects": [
    {"target": "EventInformation.js", "source": "EventInformation_bootstrap.js"}
  ]
}
```

DLL 只在文件名匹配且路径不含 `originals` 时重定向。

## 七、EnigmaVB 加壳机制

### 关键发现

**打包方式**: Enigma Virtual Box 免费版，**明文存储，零加密**。
- 4176 个文件全部 original_size == stored_size（无压缩）
- 94 个 .js 文件全明文
- 验证来源: Enigma 官方论坛 + evbunpack 源码分析

### VFS 行为

```
Game.exe 启动
  → Enigma Loader (.enigma2 节，aplib 压缩) 最先执行
  → Hook Windows 文件 API (CreateFileW/ReadFile/NtCreateFile/LoadLibrary)
  → NW.js 初始化
  → NW.js 请求文件 → Enigma Hook 拦截
    → 在 VFS 中? → 从 overlay 返回明文
    → 不在 VFS? → 返回 INVALID_HANDLE_VALUE
      → 但路径在 www/ 外? → 透传到真实磁盘
```

**我们的利用点（VFS fallback）**:
- PluginManager.loadScript("js/plugins/QuestLog.js")
- Enigma 查 VFS → 不存在 → 返回 INVALID_HANDLE_VALUE
- NW.js fallback: 去磁盘找 `www/js/plugins/QuestLog.js`
- 我们把插件文件放在磁盘上 → 成功加载

**为什么 NtReadFile 路线失败**:
- Enigma 在 kernel32 ReadFile 层拦截 VFS 文件并直接返回
- VFS 文件到达不了 ntdll NtReadFile
- NtReadFile hook 只能看到 Enigma 读自身 overlay 的 PE 数据

## 八、完整踩坑清单

### 编译环境

| 坑 | 原因 | 解决 |
|----|------|------|
| Git Bash 中 gcc 路径映射 bug | MSYS2 的 `--prefix` 导致路径不兼容 | 必须通过 MSYS2 shell 编译 |
| `__forceinline` 不兼容 GCC | MSVC 关键字 | 改用 `static` |
| MinHook `#include "../include/"` 路径错 | 项目结构变化 | sed 修正 include |
| `-Wl,--kill-at` 缺少 | MinGW 默认给导出加 @ 后缀 | 加 `--kill-at` |

### Enigma / 游戏

| 坑 | 原因 | 解决 |
|----|------|------|
| V8 Script::Compile/Run Total=0 | NW.js 0.93 不走公开 V8 API | 放弃 V8 路线 |
| BeforeCallEntered NFU 崩溃 | V8 重入墙 | 放弃 V8 回调 |
| 渲染进程 ReadFile 无 JS | JS 在浏览器进程加载 | 切到浏览器进程 |
| NtReadFile 只有 PE 数据 | Enigma 在 kernel32 层处理 VFS | 放弃 NtReadFile |
| version 代理导致残留进程 | 同名 DLL 模块依赖冲突 | 导出 return 0 |
| CWD=TEMP → nw_elf.dll | Enigma 在当前目录找 VFS | `cwd=gd` |
| P5/U5 竞态 | 多线程 ReadFile 的 unhook 窗口 | MinHook |

### Python / 打包

| 坑 | 原因 | 解决 |
|----|------|------|
| `__file__` 在打包后未定义 | bootloader 运行时不设 `__file__` | try/except sys.executable |
| `_dll_data.py` 编码错误 | 缺少 UTF-8 声明 | 加 encoding |

### 工作目录（最重要的教训）

```
正确: CWD = 游戏目录  → Enigma 找到 VFS → nw_elf.dll 加载成功
错误: CWD = TEMP       → Enigma 找不到 VFS → cannot load library nw_elf.dll
错误: CWD = 桌面       → 同上
错误: CWD 未设         → 继承父进程 CWD → 不确定
```

**黄金规则**: Game.exe 的当前工作目录**必须是**游戏目录。任何启动 Game.exe 的代码必须显式设置 `cwd=gd`。
